## 已修复的代码问题

1. **模型输出帧的归属错配。** 实际配置 window=96、context=94、feature_lag_frames=3，输出需等待4帧（160ms）。输入0–4帧时只能产出第0帧；下一批输入5–9帧时才产出1–5帧。旧实现给整批产物标记当前输入批次的 visible、generation、turn、mode，导致不可见预热转可见时，把旧的1–4帧配给新音频。现在逐帧保留输入归属，直到对应模型输出出现；渲染后继续携带归属，过期/不可见帧不会挤占新音频位置。没有移动音轨、加速视频或改模型数值计算。
2. **聆听缓冲预算缺少模型等待量。** 200ms输入、160ms输出段需要容纳输入5帧、分段余数最多3帧、模型等待4帧。最低预算从8帧改为12帧，即5120→7680个16kHz采样点（0.32→0.48秒）；否则修正帧归属后可能等待自己的未来帧而停住。回归测试模拟100个输入批次，验证不会卡死。这不是降低帧率或截断模型历史。
3. **不同页面混用LLM历史。** 旧版本一个进程共用一套对话，验收问题和用户问题混在一起。页面现在保存会话ID，同一页面重连保留上下文；不同ID接管时取消旧对话管线，重建识别缓存、上下文和请求状态，复用ASR模型权重，不重启TTS模型服务。仍为单活会话，不提供跨页面历史存档。
4. **连续对话提示。** 明确要求直接回答当前问题，除非当前询问身份，否则不重复自我介绍。但重放原混乱历史时，仅改提示词仍有1/3普通问题重复介绍（旧提示为2/3）；因此不把提示词单独宣称为彻底修复。两次真实浏览器测试共六轮普通问题未出现固定开场白，历史在同一页面持续保留。

## 为什么仍有卡顿

原本机SSH隧道在4–6分钟内反复关闭。两条隔离SSH连接分别开启/关闭WebSocket心跳，仍在286.75秒/289.66秒终止。平台公开页面的麦克风、媒体、日志连接也在约245秒同时关闭。可排除“只要本地端口映射就必然卡”的说法；已定位为这条长连接链路不稳定，尚未确认具体是哪一级代理或网络设备关闭它。

保留方案：独立的本机2238 HTTP轮询桥接→sunxc-v1原8022→SSH→GPU18788；本机映射端口18796。复用现有已授权路由和SSH主机公钥校验，TLS校验开启，不写出凭据。没有修改共享2226或服务端8022。HTTP请求持续轮换，六分钟测试未发生断线，但交付抖动比本次公开页面更大，因此它是暂时可持续交流的入口，并非延迟优化成功。

六分钟测试结束后继续保持连接，在建连约18分56秒时，HTTP隧道也遇到一次TLS连接建立失败并退出。因此该入口同样不能承诺长期稳定。已手动恢复入口。自动重建脚本已写入 `http_tunnel/Watch-OpenVAHttp.ps1`，但启动该后台进程被自动审批以 `blocked by policy` 拒绝，未给出具体理由；**自动恢复未启用**。重建网络入口也不等于无缝恢复浏览器媒体，断线后仍可能需要重新点“开始”。
