# 2026-11-01：3.8 服务逐项对比、显存与首声等待

本轮在同一张 **49140 MiB RTX 4090** 上完成九组独立服务测试。固定负载的整卡
观测峰值从 **34347 MiB（33.54 GiB）降到 9501 MiB（9.28 GiB）**；随后使用生产
默认回答策略测试长问题、长首句和连续会话，最高 **9545 MiB（9.32 GiB）**；
继续实际浏览器播放采样，最高 **9885 MiB（9.65 GiB）**。
相对 12288 MiB 预算，按所有样本的最高观测值，余量为 **2403 MiB（2.35 GiB）**。
这是 48GB 卡上的实测，尚未在真实 12GB 卡验收，也不是任意时长输入的容量保证。

## 方法与逐项结果

基线 `73a2d4846172ad1e1ea1037b5294b922113e8de9`，候选推理代码
`dbdb4ce`。每组重启独立的 TTS/动作/渲染进程，加载同一套已校验权重、头像和
参考声音；启动前及退出后确认 GPU 无计算进程。整卡显存每约 0.5 秒采样，覆盖
启动、60 秒三轮短问题和一轮 16 秒长问题，不累加组件节省量。

统一使用 API 型号 `qwen3.8-flash`，关闭思考、hedge 和搜索。对比负载使用相同的
两句回答，九组每组四轮的句子长度和 SHA-256 全部一致。
固定回答对比温度为 0；正常回复测试恢复生产温度 0.3，原有最大三句、256 tokens
上限保持不变。输出保持 512×512、
`PIPE_FRAME_STRIDE=1`，动作步数 1、VoxCPM2 步数 10；沿用原始精度、全部五路
CFG 和既有闲置整理策略，`DYSTREAM_AUDIO_HISTORY_MAX_SEC=0`，没有新增历史截断。

## 找到的显存大头

只按 4、8、16、32 秒跳跃测试，会漏掉连续服务的分配行为。以真实训练权重重放
**182 个输入长度**，每次增加五个姿态帧（0.2 秒），最长 40.16 秒，两路音频均保留：

| 动作子进程 | 峰值活跃张量 MiB | 最大 reserved MiB |
| --- | ---: | ---: |
| 默认分配器 | 2070.98 | 20828 |
| expandable segments | 2061.78 | 2146 |

182 个长度的两路音频特征 SHA-256 全部一致。大幅差异来自分配器保留的存储，
不意味着模型权重或必要张量本来就有 20 GiB。
[PyTorch 2.8 官方说明](https://docs.pytorch.org/docs/2.8/notes/cuda.html#optimizing-memory-usage-with-pytorch-cuda-alloc-conf)
描述了逐渐增大的分配请求如何留下难以复用的空间，以及可扩展段的处理方式。
随后才运行上面的完整服务测试，整卡结果并非由此子进程数据推算。

验证后的部署配置：

```bash
DYSTREAM_FOLD_EMA=1
DYSTREAM_CACHE_SPECTRAL_NORM=1
DYSTREAM_RELEASE_RENDER_INTERMEDIATES=1
PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
```

分配器设置须在模型进程首次初始化 CUDA 前生效，并由 TTS 与动作/渲染进程共同继承。
本轮没有开启 CPU 词表卸载、CFG 裁剪或条件投影重用。

## 长问题为什么慢

生产默认回答策略下，按请求 ID、TTS context 和文本哈希关联运行时事件：

| 测试情形 | 首句字数 | 首正文→首句释放 | TTS 请求→首 PCM | 说完→首 PCM | 说完→音画边界 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 短问题，连续会话中生成较长首句 | 67 | 983 ms | 156 ms | 2654 ms | 3209 ms |
| 16 秒长问题，简短开场句 | 3 | 36 ms | 176 ms | 1259 ms | 1837 ms |
| 要求完整长句解释 | 92 | **1146 ms** | 157 ms | **2391 ms** | **3022 ms** |

最后一行的 TTS 请求比 LLM 流结束晚约 1.3 ms，确实在等整句生成完成。
第二行 TTS 则在 LLM 流结束前已开始，首 PCM 也早于流结束。因此：

1. Paraformer 是流式 ASR。16 秒问题发生了 30 次识别调用；该例最慢单次约
   256 ms，小于 600 ms 音频块。结束时只刷新尾块。
2. **LLM→TTS 存在完整句缓冲**。首句很长或整段只有一句时，表现为接近全文
   生成完才启动 TTS。这一情形复现了用户怀疑的等待。
3. VoxCPM2 接收完整句文字，随后流式输出音频；没有等待整段音频合成完再返回。
4. Edge 实际检查另测到：说完→首 PCM 日志到达 1742 ms，→媒体边界到达
   2534 ms，→视频解除静音 3578 ms。解除静音时播放位置正好到达安全边界；
   控制事件到达后仍等约 **1044 ms**。这不是物理声卡首声测量。

第二次 Edge 重测为首 PCM 日志到达 1697 ms、媒体边界到达 2237 ms、解除静音
2877 ms，后两者间隔约 640 ms；该次同时记录了上面的 9885 MiB 整卡峰值。
浏览器缓冲等待有波动，不能用单次结果声称固定减少某个时长。

不能将“输入长”直接当作主因：该长问题首句短，反而比短问题但首句长的例子更快。
独立 3.8 API 三次长首句测试也记录了约 0.89–1.09 秒的句子积攒时间。

对照：[Pipecat 聚合粒度](https://reference-server.pipecat.ai/en/stable/api/pipecat.services.tts_service.html)、
[LiveKit 提前生成与取消](https://docs.livekit.io/agents/logic/turns/tuning/)、
[CosyVoice 2 流式合成论文](https://arxiv.org/abs/2412.10117)。本轮保持现有分句和
声音模型；提前生成需验证转写变动后的取消，文本双流不能只靠切换一个聚合标志获得。

简易探针另修复了旧轮媒体事件导致负延迟的问题，复用正式基准的
`AssistantTurnLifecycle`；两项真实 WebSocket 回归通过。旧失败尝试保留，只采用
修正后匹配同一轮、同一代事件且具有首 PCM 的数据。
