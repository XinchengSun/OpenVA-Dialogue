## 实际问题

用户反馈10秒等待之后重新取证，服务器历史样本中 LLM 首token约0.48–0.68秒、TTS首块约0.13–0.15秒。只能说明这些样本的生成并不需要10秒，不能排除其他轮次慢。最初三条AV队列满发生在连接启动，不能据此解释整个对话。

前端之前强制1倍速但完全不恢复积压。一旦聆听播放停滞，后续回复还要排在旧静音画面后面。此前145秒没有 `waiting` 的测试并未度量这种持续落后，因此不足以验收交互延迟；先前由短测推及整体可用的结论过早。

另一次公开代理实播出现声音停顿时，服务器仍持续以25fps写出音视频，浏览器媒体缓冲却落后数秒。说明输出后的传输/交付存在问题；当前证据不能精确区分平台代理、网络、客户端接收三者各占多少，也不能把用户那次10秒全部归给网络。

## 本轮修改

1. `static/index.html`：仅在尚未开始播放回复、视频静音、没有上一轮可见回复时，按服务器的回复起点清理积压的静音前缀；定位在回复起点前160ms，且必须已有完整连续区间和2秒回复缓冲。正在说话时不跳播、不加速，保留1倍速。
2. 保留2秒播放储备。最初尝试只留0.4秒虽能快开口，但完整多轮测试失败，未作为最终版本保留。静音前缀恢复会跳过部分旧聆听画面，可能出现一次视觉跳转；不能称完整画面时间序列完全未变。
3. 日志DOM更新合并到250ms一次，关闭日志面板时不逐行触发布局。没有单独量化它的性能收益。
4. 每5秒记录数值型播放位置、缓冲量、暂停/静音、帧数，便于下次实际用户浏览器定位；不在此遥测中上传音频或问答内容。

## 浏览器实测

独立 headless Edge，真实 getUserMedia 文件麦克风和MSE播放；不是给LLM发文字模拟语音。延迟定义为输入PCM最后一个超过幅度阈值的样本，到第一次检测到该回复音视频已解除静音并开始播放；视频每100ms采样。不是物理扬声器收音测量。

| 测试条件 | 说完到开始播放 | 播放缓冲结果 |
| --- | --- | --- |
| 原前端，公开代理，人为暂停聆听8秒 | 12.42秒 | 无waiting仍可积压，回复边界收到后额外等10.20秒 |
| 中间版0.4秒储备，同样人为暂停8秒 | 3.13秒 | 单轮通过；随后145秒多轮故事内卡3次，累计8.83秒，因此不保留此配置 |
| 最终2秒储备，公开代理，同样暂停8秒 | 5.15秒 | 静音区恢复8.25秒积压；定位产生9.1ms等待，回复内无卡顿；边界收到后额外2.19秒 |
| 最终2秒储备，本机直连，145秒三轮 | 4.89 / 4.68 / 4.91秒 | 聆听与说话waiting/stalled均0，无跳播、全程1倍速 |

两条路由的三轮输入一致，但测试先后进行、网络与对话历史不同、LLM生成的故事也不同，因此不能称严格同输出随机A/B，更不能保证所有后续请求都在5秒以内。8秒暂停是人为故障注入，不是对用户原始那次10秒的直接重放。

直连三轮播放音轨重新识别为“三”“北京”和完整木匠木鸟故事。故事媒体区间78.00–102.60秒（24.6秒，含边界余量），结尾为“每当风吹过屋檐……仿佛老木匠从未离开”，已通过结束边界正常回到聆听。视频解码为H.264 512×512、25/1 fps，音频AAC。浏览器累计7个丢帧/3575帧，不能称逐帧零丢失；没有缓冲停顿。自动转写有识别误差，不代替人工音质评价。
